## Historical implementation and measured evidence

Historical `b95b6a7` had pandas DataFrames, Python `dict[str, dict[str, CandidateProvenance]]` for all S1 queries, Python postings lists, and per-query loops. Its retrieval fit constructed name **and address** TF-IDF matrices for all 10.3M targets, with optional word TF-IDF, then `sub_mat.dot(target_matrix.T)` generated a full sparse product for each batch before selecting top-K per row. A common n-gram can create huge intermediate nnz despite top-K retention afterward. The pipeline defaulted to five graph-aware folds and performed expensive candidate materialization. In training it sorted candidate lists using `item[0] in true_targets` and retained true targets ahead of negatives; that is a label-dependent training set, so it cannot be used as evidence that inference cap recall is high. Later commits introduced GPU paths, which are irrelevant to the available CPU machine.

The repository history has repeated OOM and performance fixes (`18bd42c`, `bc6e11e`, `c077a74`, `9d0a35d`), showing that batching alone did not settle architecture cost. Historical commit `68d1eb1` records a **measured** pilot: file-store normalization/index preparation for all train rows in 356.7 s at 2.6 GB on a 12-core/15-GB machine; exact-name top-K=50 truncation missed 1.33% of clean-name hits and 2.98% of core-name hits. A 400-S1 demonstration with just 16.4k selected targets got 0.995 candidate pair recall and ~0.977 entity F0.5, but it was intentionally easy and cannot predict full-scale performance. That report explicitly states no full-scale freeze or test inference. No current full-run measurement or final model exists.

There is no evidence in the current code for a SQL computation backbone. History mentions a deprecated SQLite store replaced by file-store work; the expensive current historical paths are primarily Python-object candidate structures and unbounded sparse intermediate products. The redesign therefore excludes SQL as a default without claiming a measured SQL bottleneck that the repository does not substantiate.

## Keep / replace decisions

Keep the competition statement and official validator as contract, but add stricter internal checks. Use historical normalizer/feature ideas as test cases, not as code to copy blindly. Replace pandas/Python-object global candidate maps, all-query name+address KNN, full sparse products, compulsory five-fold OOF, label-prioritized retrieval evidence, and GPU requirements with the staged design in `architecture.md`. Retain a deterministic entity split and exact entity metric. Revalidate all historical pilot numbers on the new pipeline. Phase 1 begins with data contract/profiling and fixed dev/AWS configs; no model or candidate quality claim exists yet.

# CPU-first business entity resolution architecture

Status: design baseline, 2026-09-26. The competition statement in `README.md` is authoritative. Numerical budgets below are targets, not measured results. No external business identity data, geocoding, APIs, or enrichment may enter any stage. The current checkout has only an empty entry point and empty requirements; historical commits contain the old implementation, not a runnable baseline in this checkout. A historical 2026-09-25 pilot reported a 356.7-second streaming file-store build at 2.6 GB, but only a 400-S1 retrieval/model demo against 16.4k targets; that demo cannot establish full-scale recall or runtime. It also found exact-name top-K truncation lost 1.3–3.0% of exact hits at K=50. These are historical measurements to revalidate, not current baseline results.

## 1. Problem, metric, and scale

Source 1 (S1) is the reference. For each S1 row, predict a set of zero, one, or several IDs from S2 and S3. There is no one-to-one constraint. Inputs are UTF-8 TSVs with `entity_id`, `business_name`, `business_address`, `country`; train truth has `source1_entity_id` and comma-separated `matched_entity_ids`. Preserve blank strings. Training has 2,206,821 S1, 5,034,616 S2, 5,285,603 S3 rows; test has 1,732,544 S1, 4,887,273 S2, 5,082,316 S3 rows. These counts are supplied targets to verify in Phase 1.

The official objective is **macro entity F0.5**: for each S1 entity with nonempty truth, P=TP/(TP+FP), R=TP/(TP+FN), F=1.25PR/(0.25P+R), with zero if either needed denominator or TP is zero. Empty truth and empty prediction scores 1; empty truth and nonempty prediction scores 0. Average over *all* S1 entities. Keep micro precision/recall and pair PR-AUC as diagnostics only. The published example gives 0.714 for P=2/3 and R=1; implementation must reproduce it and other independent hand calculations. Singleton prevalence and cardinality distribution are Phase 1 measurements, never assumptions.

## 2. Resources and execution contract

Target 8-vCPU/64-GB CPU server: training ~3 h, inference ~2 h, practical RSS <=45–50 GB. Laptop: 12 cores/16 GB, deterministic S1 sample with the same algorithms and entire relevant target index only when profiled safe; sample and target scope are explicitly recorded. No CPU pipeline promises these targets until full throughput is measured. Pipeline emits per-stage wall time, peak RSS, row counts, artifact bytes, thread count, and extrapolated full-scale time with uncertainty. A stage whose projected budget is materially exceeded is reworked before adding downstream work.

Use bounded batches and memory mapping where practical; 250k–1M feature pairs per batch starts the benchmark. Example: 2.206M x 20 = 44.1M pairs, so storing Python objects per pair is unacceptable. Pair keys are compact integer row IDs plus source identifier; IDs remain mapped to original strings. A 10M x 50M dense similarity matrix is forbidden. CSR memory estimate is `nnz*(data_bytes + index_bytes) + (rows+1)*indptr_bytes`, plus index, transpose and multiplication workspace, with 2–3x measured safety headroom. Float32 scores and int32 indices are preferred only when shapes fit; never silently overflow. Reserve memory explicitly for Polars/Arrow buffers, LightGBM, and OS cache.

## 3. Data flow and boundaries

```text
raw TSV -> schema/profile -> normalized Parquet
                           -> exact/core and rare/numeric indexes
                           -> gated sparse char TF-IDF top-K
                           -> union/dedup/refine/cap -> final candidate Parquet
                           -> batched pair feature Parquet
                           -> positive + hard/easy negative sample -> LightGBM
                           -> validation pair scores -> entity zero/one/many policy
                           -> cached threshold search -> frozen model/config
test TSV -> same frozen transforms/retrieval/features/scorer/policy
         -> matching_results.tsv + candidate_pairs.tsv -> official validator
```

Module boundaries under `chimera_submission/code/business_entity_resolution/src/`: `config`, `data`, `normalization`, `blocking`, `retrieval`, `features`, `training`, `scoring`, `entity_decision`, `evaluation`, `inference`, `output`, `utils`. `CandidateRetriever.retrieve(batch)`, `PairFeatureBuilder.transform(batch)`, and `PairScorer.fit/predict` accept versioned schemas and return bounded Arrow/Parquet batches or NumPy arrays. CPU implementations are first; future GPU components may implement these interfaces without changing artifact schemas. No GPU dependency in V1. A lightweight orchestration entry point uses stage signatures and cache manifests; it does not retain all pairs in memory.

## 4. Storage, cache, and reproducibility

`artifacts/{profile,normalized,indexes,tfidf,blocking,candidates,features,training,models,predictions,validation,reports}/` holds deterministic, stage-specific outputs; `reports/ablation.csv` records experiments. Artifacts are ignored by Git. Each manifest records code commit, input file size/hash or reliable fingerprint, schema version, relevant config hash, seed, row count, bytes, elapsed time, peak RSS, and upstream artifact signatures. Atomic temporary write + rename prevents partial reuse. Changing thresholds invalidates decision/metrics only; model parameters invalidate model/scores/decisions; feature version invalidates features and downstream; candidate configuration invalidates candidates and downstream; normalization invalidates all later stages. Reuse the same candidate file for model experiments. Never cache labels in test artifacts. Pin Python and package versions in requirements; record effective thread environment, seed, and git SHA.

`configs/dev.yaml` and `configs/aws_cpu.yaml` centralize paths, sample hash, threads, batch sizes, block limits, TF-IDF settings, candidate cap, memory and stage budgets. Dev sample is selected by stable hash of S1 ID, independent of row order, including singleton and multi-match cases via a separately reported stratified diagnostic sample; any stratification uses train labels only. The production candidate universe is always all S2/S3 within the dataset split. Train and test indexes are separate to avoid accidental cross-split matches. Validation S1 IDs are held out together with *all* their candidate pairs; S2/S3 indexes can be shared as unlabeled retrieval corpus, but their labels cannot leak. A connected-component split is optional only if measured identity overlap creates leakage risk.

## 5. Normalization and country/address parsing

Retain `name_raw` and `address_raw`; emit `name_clean` (NFKC, casefold, controlled punctuation and whitespace, `&`/`and` equivalence), `name_core` (strip legal suffix tokens only at safe token boundaries), `address_clean`, `address_numbers`, and `postal_candidate`. Empty stays empty. `co` is ambiguous and needs an ablation before removal. Normalize common `pvt/private`, `ltd/limited`, `llc`, `inc/incorporated`, `corp/corporation`, `company` safely. Keep names with all suffix tokens from collapsing to empty by falling back to clean name. Never erase raw evidence.

Country is an open-set normalized string. Feature values are `country_same`, `country_different`, `country_missing`; country may refine blocks when both fields are present, but unknown labels must flow through. Address parsers are dispatchable by country, with a generic fallback. India: six-digit PIN, flat/plot/door/building numbers, road aliases, colony/nagar/district/state-like tokens. US: ZIP/ZIP+4, street number, unit/suite, street aliases. France/generic: postal-looking tokens, numeric tokens, word tokens; no reliance on external postal tables. Postal mismatch is evidence, not an absolute veto, because addresses can be incomplete or wrong.

## 6. Retrieval and candidate control

Index S2 and S3 jointly but retain source code and source ID. Channel A exact `name_clean`; B exact `name_core`. An inverted index stores key -> contiguous sorted target row IDs and block cardinality, preferably Arrow/NumPy arrays instead of Python lists of objects. Very common keys use country, postal, number and additional rare-name-token refinements; unresolved oversize blocks emit a bounded, deterministic best-evidence subset. Report original and refined size, trimmed queries, and exact GT loss; never silently drop. Historical exact top-K truncation already showed measurable loss, so compare any new refinement against that failure explicitly.

Channel C rare name tokens: compute document frequency over target records (once per unique token per record), exclude high-frequency tokens, select a few high-IDF tokens per query, limit postings scanned, and rank by shared rare tokens/IDF plus cheap name evidence. Channel D uses name evidence *with* postal or house/building number. Common numbers or postal codes alone never cause global joins. Cap postings and output per channel before union. Country mismatch may downrank but should be measured before hard filtering.

Channel E is character 3–5 gram TF-IDF over names, sparse CSR, float32, a frozen train-fitted vocabulary/IDF for test. Initial implementation benchmarks `sparse-dot-topn` query batches against target CSR transpose, retaining only top-N above a measured threshold; do not materialize the full sparse product. Very high-frequency n-grams may still produce enormous intermediate products; estimate batch nnz, use bounded query batches, max feature frequency/`min_df`, and measure multiplication workspace. If global name index is too large, benchmark deterministic country partitions with a generic/missing-country fallback and quantify lost recall. No global address KNN in V1.

Two-stage cascade: run cheap channels for all S1; send unresolved/uncertain queries to TF-IDF. Starting gate: fuzzy if no cheap candidate has strong *retrieval evidence* (e.g. unique exact/core name with compatible postal/number) or if cheap list is empty. This is only a hypothesis; on validation, compare with an all-query fuzzy audit sample to estimate GT lost by gating and false-confidence rates. Adjust gate to protect recall. A cheap exact name with many targets is uncertain. Gating must be deterministic and labels-free at inference.

Union channels by `(s1_row_id,target_source,target_row_id)`; OR provenance flags, preserve best TF-IDF score/rank and exact block size. Rank cheaply using channel agreement, rarity, exactness, postal/number agreement and name similarity on only bounded preselection. Use deterministic ties by target ID. Audit candidates *before* and *after* cap K=5,10,15,20,30; start production at K=20 only if measured recall/latency supports it. The final candidate Parquet is exactly what the model scores and what `candidate_pairs.tsv` later serializes. Retrieval cannot access truth to rescue positives; positives absent from candidates count as misses.

Blocking report per channel, union, and each cap: total pairs; mean, median, P90/P95/P99/max pairs per S1 (including zero); GT pairs and pair recall; entity any-hit and complete recall; unique GT recovered per channel (including marginal over cheaper channels); oversized block and trimming distributions; elapsed time, RSS, and artifact bytes. Measure country and truth-cardinality slices. Oracle entity F0.5 with perfect labels among candidates is a useful ceiling, never a model score.

## 7. Features, training, and validation

Pair features are generated in bounded candidate batches. The CPU implementation loads normalized Arrow columns once, maps entity IDs to integer row indices, and gathers only rows used by each candidate batch; this avoids rebuilding a 10M-row hash join for every candidate shard. V1 keeps high-value, measurable features: exact clean/core name; RapidFuzz ratio and token-set ratio; word Jaccard/intersection; length ratio; prefix/suffix agreement; retrieved TF-IDF cosine and rank; exact/soft address similarity; postal equal/conflict/missing; numeric overlap and contradiction; country relation; provenance, channel count, exact block size. Expensive normalized Levenshtein/Jaro-Winkler and redundant variants are added only after feature timing and ablation. Missingness uses explicit flags; a numeric zero is accompanied by the relevant provenance or missingness flag. Keep features numeric and finite. Parquet partitions are sized for sequential reading and bounded artifacts.

Train on *all retrieved positives* and sampled negatives: high-scoring TF-IDF, exact/core-name collisions, same postal/name and top incorrect candidates are hard negatives; a small deterministic random/easy sample broadens coverage. Try 1:5, 1:10, 1:20 positive:negative subject to memory. Training sampling never changes validation candidate distribution. If class weighting or calibration is used, measure its effect on entity F0.5. LightGBM CPU baseline uses ~8 threads on AWS, seed, early stopping on held-out entities, moderate leaves/depth, learning rate 0.03–0.08, feature/bagging fraction ~0.8. Save model, feature order, and training manifest. Pair PR-AUC/precision/recall and importance are diagnostics.

Split by stable hash of S1 ID (~85/15 initially) before pair construction; keep all pairs of an S1 together. Training can use all S2/S3 records as unlabeled retrieval corpus. Thresholds are selected only on held-out S1 labels and cached pair predictions, never on test score distributions. After tuning, Phase 15 trains a final scorer on all labeled training S1 pairs using the chosen feature/negative policy; preserve the held-out validation report from the pre-refit model and note that the refit model is not independently validated. Reuse frozen normalization/retrieval transforms, including TF-IDF vocabulary fit on allowed training corpus only. Optional stronger grouped or cross-fitted validation occurs only if measured need and budget permit.

## 8. Entity decision and error analysis

Sort scores within each S1; retain top 3, top-second gap, candidate count, top-k mean, channel agreement and ranks. A deterministic policy has singleton threshold, strong-match threshold, pair inclusion threshold, gap threshold, and optional max count. Below singleton threshold return empty; a strong isolated top can return one; otherwise return all candidates above pair threshold. Handle 0/1/many; never force top-1. Threshold search is coarse-to-fine on cached validation scores, evaluating *exact* macro F0.5 and adjacent settings for stability. Report macro score, micro P/R, singleton accuracy/false-positive rate, and true/predicted 0/1/many confusion. A policy that gains a tiny score at a brittle point is rejected for a stable neighborhood. Any material upstream score change requires re-optimization.

Phase 13 assigns errors to retrieval miss, retrieved-but-ranked-wrong, singleton false positive, missed match, wrong top-1, extra multi-match miss, normalization failure, address conflict, common-name ambiguity, country issue, numeric/postal conflict. Review representative cases with IDs and permitted provided fields only. `reports/ablation.csv` stores experiment ID, channels, K, features, negative policy, model, thresholds, candidate recall, any/complete hit, micro P/R, macro F0.5, runtime, peak RSS, and notes. Phase 14 changes a component only for a quantified failure class and keeps it only when full entity F0.5 gain justifies runtime/RAM.

## 9. Production inference and output

Test uses frozen config, normalizer, indexes/TF-IDF vectorizer, feature schema, model, policy. It processes all 1.73M S1 rows in batches, writes atomic outputs and stage profiles, and requires ~2 h measured target. Emit exactly one row per S1 in each UTF-8 TSV, comma-separated unique valid S2/S3 IDs, empty list as blank after tab, deterministic order. Output paths are `chimera_submission/output/matching_results.tsv` and `chimera_submission/output/candidate_pairs.tsv`. The latter is the *post-prune/post-cap candidate set actually scored*. Internal validation checks matched subset of candidates and test ID membership; run `python3 utils/validate_submission.py --matching ... --candidate ... --test-dir dataset/student_resource/dataset/test --check-ids`. Its subset violation is only a warning, so internal validation must make it fatal. The validator's default test-dir differs from this checkout's nested path.

## 10. Failure modes and explicit decisions

| Decision | Reason / expected ML effect | Rejected alternative | Runtime / RAM implication |
| --- | --- | --- | --- |
| One deterministic S1 split first | Gives entity-level selection quickly; optional stronger CV later | Mandatory five full OOF folds and graph components from legacy | Cuts repeated retrieval/model runs; lower peak due to caching |
| Bounded arrays/Parquet candidate tables | Makes ~44M pairs feasible and auditable; protects recall with cap sweep | Legacy nested Python dict/list per pair and pandas row loops | Streaming memory; bounded I/O |
| Sparse top-N name TF-IDF only for uncertain queries | Recovers lexical variants within budget | Global address + word + name KNN for every S1; full sparse product | Fewer dot products and smaller workspace; gate loss measured |
| Exact/rare/numeric blocks with frequency refinement | Cheap recall from complementary evidence | Unbounded exact key/postal cross join, SQL backbone | Postings and pair count capped; RAM depends on compact indexes |
| Truth-free retrieval, measure misses | Honest recall ceiling | Inject missing truth pairs into training or candidate evaluation | No hidden label-dependent work; may lower apparent score |
| Pair LightGBM + deterministic set policy | Strong lexical/address interactions, explicit singleton/multi-match | Immediate meta-model, ensembles, calibration, neural reranker | CPU-feasible training; lower model memory |
| Open-set country relation and generic parser | France/future labels survive | Closed country one-hot or country-only hard filter | Minimal extra runtime/RAM; avoids domain exclusion |
| Stage caches with keyed invalidation | Fast model/threshold iteration | Re-run normalization and retrieval per experiment | Disk cost traded for hours saved |
| CPU-only initial stack | Meets available AWS machine | Legacy CUDA/Torch/FAISS paths | No GPU memory/dependency; GPU adapters remain possible |

Potential failures: malformed TSV/UTF-8, duplicate IDs, missing truth rows, huge common blocks, TF-IDF n-gram explosion, high RAM during joins, false-confidence cascade gate, singleton overmatching, unrepresentative dev sample, France shift, output IDs not in test, interrupted artifacts. Each has an explicit Phase 1/3/5/7/12/17 validation or performance gate; stop at the failing phase, profile, revise config/algorithm, document recall and F0.5 effects, then proceed.
